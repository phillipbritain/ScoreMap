# Scenarios for local runs: a fake feed in the server, picked in the app, at real venues

Run locally, ScoreMap shows a scenario by default rather than real games, so its look and its live updates can be checked at any time without waiting for real games to start; real ESPN data matters mostly on the deployed site, and stays one choice in the app. Scenarios exist only when the server runs in Development, so the deployed site can never show made-up scores.

The made-up games come from a fake game feed provider in the server, in place of ESPN's (ADR-0001), rather than from a fake ESPN server or from fakes in the browser. Everything after the feed (the game board's statuses, windows and change events, the venue locator, the poller and the hub, and the browser app) is the real code, and scenarios are JSON files in ScoreMap's own terms rather than in ESPN's unofficial response shape. Games are written out one by one, apart from three shorthands kept deliberately few: `fill` (N games from a named group of venues, in a status mix that is part of it), `"play": true` (the games play like real games) and `"disrupted"` (the share of them Disrupted under play). Fake games can be in any configured league at any venue, so the settings menu stays the same as in production.

The default scenario (`worldwide`) is the `Scenario` setting in `appsettings.Development.json`, overridden by `scripts/dev.ps1 start -Scenario <name>` (`real` for real games). A floating pill over the globe switches between scenarios, and to real games, while running. Media keys beside it (Pause, Play and Fast-forward) set the speed, and the scenario clock is shown over the globe. Because the server holds one set of games for every browser, it runs one scenario at a time, and switching it in one tab switches it in all of them; a scenario per tab would have needed a game board per connection, for testing alone.

Scenarios use real venues, from a hand-written list in the repo, so pin placement is tested on real places. Their lookups are made once by a script and checked into the repo as `scenario-venue-locations.json`, which the venue locator checks before its saved lookups, rather than made through Nominatim at runtime: at one lookup every 1.5 s, the default scenario's 150 venues would take nearly 4 minutes on every new machine. The price is a file to regenerate when the venue list changes, and scenario pins seldom exercise a live Nominatim lookup (only the edge-cases scenario's deliberately unfindable venue does).

## Consequences

- With the poller's real intervals (15 s while a league has Live games, 3 min otherwise) a scripted change would show up to minutes late, so in scenario mode every league is fetched every second, divided by the speed but no more often than every 250 ms, so that at high speeds a script's changes don't arrive bunched together. The intervals become settings, but the poller's logic doesn't change.
- A looping script restarts with fresh copies of its games under new ids, and the old copies drop out of the feed, so no game ever goes back from Final to Live. Play likewise lets a Final or Disrupted game stay a short while (a minute of scenario time), then replaces it with a new game from the fill's group of venues, rather than letting games run forever.
- Scenarios that play, play like real games: Live games score, their clocks run, they go to breaks and finish, Upcoming games start, and some games are disrupted. Play replaced two kinds, random play (`"play": "random"`) and live play (`"play": "live"`), where Live games scored and ran but no game changed status, came or went, so a scenario kept its fixed mix. Live play was for scenarios about something other than games changing, but in use a scenario that never starts, finishes or brings on a game didn't look like real games, and no scenario needed a fixed mix any more, so `"play": true` is the only kind left. A written-out Live game plays on from its written period and clock. The edge-cases scenario has no play, so its extremes (a tie, three-digit scores) stay put, and empty has no games to play.
- Play disrupts games as real ones are: an Upcoming game is Postponed or Canceled before it starts, so it has no score, and a Live one is Suspended, keeping its score and period. `"disrupted"` (0.05 if left out) is the share of the games showing at any moment that are Disrupted, and play steers towards it, disrupting games when there are too few, rather than giving each game a fixed chance, so the share holds however many games come and go: 0.05 of 150 games is about 7 or 8 Disrupted pins. It also sets the share at the start: a fill starts that share of its games Disrupted, so a fill's mix no longer takes `disrupted`. The scenario files that play still write `"disrupted": 0.05`, so the value is there to change, and a scenario without play can't set it, since nothing would act on it.
- Fewer scenarios ship, since the two that play (worldwide and crowded) cover what the others were for: `disrupted` (disrupted games next to normal ones), `busy` (steady change), `live-scoring` and `lifecycle` (scripted scoring and a game through every status) were dropped. Timelines remain for scenarios written by hand.
- Scenario times are relative to when the scenario starts, on a scenario clock: it reads the real time when the scenario starts, then runs at the chosen speed, so scenarios can be watched play out in minutes. Everything about a scenario's games is on it: scripted changes and loops, play (which moves on in steps of scenario time, so a seed gives the same games at the same reading whatever speed changes were made), start and end times, and the game board's pin windows. The server's `TimeProvider` itself is never sped up, since the poller's scheduling, the Nominatim rate limit, venue photo retries and stream link caching need real time; the game board takes the scenario clock instead while a scenario runs. An earlier version sped up the played games alone (6×) rather than a clock, which left game clocks further on than their start times suggested (80' in a game that started 20 minutes ago); a clock that speeds up keeps game clocks, start times and the clock shown in the app in agreement.
- The speeds are named and few: Paused (the clock stands still), Normal (real time), Fast (2×) and Faster (8×). The server names them, and the setting, `-Speed` and the speed endpoint take the name. Media keys pick them: Play is Normal, Pause pauses, and Fast-forward goes to Fast and, pressed again, flips between Fast and Faster; the lit key is the speed, with no label. An earlier version offered seven speeds, 1× to 64×, from a list; in use, three speeds and a pause were all that testing needed, and nothing as fast as 32× was judged useful (#70).
- The speed is one for the server, like the running scenario: changing it in one tab changes it in all of them. A change carries on from where the scenario is (the clock keeps its reading and runs at the new speed), and switching scenarios keeps the speed, so a scenario switched to while paused starts paused. It starts at the `ScenarioSpeed` setting (Normal), overridden by `scripts/dev.ps1 start -Speed <name>`. With real games running, the speed can't be changed and the clock shows the real time.
- At high speeds, short-lived states pass quickly in real time (at 8× a Final or Disrupted game under play is replaced in 7.5 seconds), since everything stays on the scenario clock rather than some waits being kept in real time.
