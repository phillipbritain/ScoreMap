# Scenarios for local runs: a fake feed in the server, picked in the app, at real venues

Run locally, ScoreMap shows a scenario by default rather than real games, so its look and its live updates can be checked at any time without waiting for real games to start; real ESPN data matters mostly on the deployed site, and stays one choice in the app. Scenarios exist only when the server runs in Development, so the deployed site can never show made-up scores.

The made-up games come from a fake game feed provider in the server, in place of ESPN's (ADR-0001), rather than from a fake ESPN server or from fakes in the browser. Everything after the feed (the game board's statuses, windows and change events, the venue locator, the poller and the hub, and the browser app) is the real code, and scenarios are JSON files in ScoreMap's own terms rather than in ESPN's unofficial response shape. Games are written out one by one, apart from three shorthands kept deliberately few: `fill` (N games from a named group of venues), a status mix for filled games, and `"play"`, either `"random"` or `"live"`. Fake games can be in any configured league at any venue, so the settings menu stays the same as in production.

The default scenario (`worldwide`) is the `Scenario` setting in `appsettings.Development.json`, overridden by `scripts/dev.ps1 start -Scenario <name>` (`real` for real games). A floating pill over the globe switches between scenarios, and to real games, while running. A second pill beside it sets the speed, and the scenario clock is shown over the globe. Because the server holds one set of games for every browser, it runs one scenario at a time, and switching it in one tab switches it in all of them; a scenario per tab would have needed a game board per connection, for testing alone.

Scenarios use real venues, from a hand-written list in the repo, so pin placement is tested on real places. Their lookups are made once by a script and checked into the repo as `scenario-venue-locations.json`, which the venue locator checks before its saved lookups, rather than made through Nominatim at runtime: at one lookup every 1.5 s, the default scenario's 150 venues would take nearly 4 minutes on every new machine. The price is a file to regenerate when the venue list changes, and scenario pins seldom exercise a live Nominatim lookup (only the edge-cases scenario's deliberately unfindable venue does).

## Consequences

- With the poller's real intervals (15 s while a league has Live games, 3 min otherwise) a scripted change would show up to minutes late, so in scenario mode every league is fetched every second, divided by the speed but no more often than every 250 ms, so that at high speeds a script's changes don't arrive bunched together. The intervals become settings, but the poller's logic doesn't change.
- A looping script restarts with fresh copies of its games under new ids, and the old copies drop out of the feed, so no game ever goes back from Final to Live. Random play likewise lets a Final game stay a short while, then replaces it with a new game, rather than letting games run forever.
- Live play (`"play": "live"`) is for scenarios about something other than games changing (every status at once, a crowd of cards, disrupted games), whose Live games would otherwise sit frozen: Live games score and their clocks run as under random play, but no game changes status, comes or goes, so the scenario keeps its mix however long it runs. A Live game at the end of its last period starts over as a fresh copy under a new id, from nil-nil, as a looping script's games do, rather than finishing, starting again in place (its score would go down) or replaying its last period (its score would climb without end). Under either kind of play a written-out Live game plays on from its written period and clock. The edge-cases scenario has no play, so its extremes (a tie, three-digit scores) stay put.
- Scenario times are relative to when the scenario starts, on a scenario clock: it reads the real time when the scenario starts, then runs at the chosen speed (1×, real time, up to 64×), so scenarios can be watched play out in minutes. Everything about a scenario's games is on it: scripted changes and loops, random play (which moves on in steps of scenario time, so a seed gives the same games at the same reading whatever speed changes were made), start and end times, and the game board's pin windows. The server's `TimeProvider` itself is never sped up, since the poller's scheduling, the Nominatim rate limit, venue photo retries and stream link caching need real time; the game board takes the scenario clock instead while a scenario runs. An earlier version sped up random play's games alone (6×) rather than a clock, which left game clocks further on than their start times suggested (80' in a game that started 20 minutes ago); a clock that speeds up keeps game clocks, start times and the clock shown in the app in agreement.
- The speed is one for the server, like the running scenario: changing it in one tab changes it in all of them. A change carries on from where the scenario is (the clock keeps its reading and runs at the new rate), and switching scenarios keeps the speed. It starts at the `ScenarioSpeed` setting (1×), overridden by `scripts/dev.ps1 start -Speed <n>`. With real games running, the speed can't be changed and the clock shows the real time.
- At high speeds, short-lived states pass quickly in real time (at 64× a Final random play game is replaced in about a second), since everything stays on the scenario clock rather than some waits being kept in real time.
