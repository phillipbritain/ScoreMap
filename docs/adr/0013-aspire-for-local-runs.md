# Aspire for local runs: one run per clone or worktree, side by side

ScoreMap runs locally through a stock .NET Aspire setup (#102): an AppHost (`server/src/ScoreMap.AppHost`) that declares the server project and the browser app (`AddViteApp`, with `WithReference(server)` so Vite's proxy gets the server's URL), and the ServiceDefaults project the server calls `AddServiceDefaults()` from. `aspire start` starts a run in the background, `aspire ps` lists the runs on the machine, `aspire describe` gives a run's URLs, and `aspire stop` stops one (`--all` stops every one). It replaced `scripts/dev.ps1`, which started the server and Vite on fixed ports (5147 and 5173), so only one run could go on the machine at a time: a second clone or git worktree, such as another agent session's, couldn't start its own. With Aspire's isolated mode (`aspire start --isolated`), a further run gets random ports, so any number of clones and worktrees each run at once, each with its own server and so its own scenario, speed and logs, and each shown in its own dashboard. The rule throughout is Aspire as its docs and templates set it up, with nothing custom: no wrapper script and no build folders of our own.

## Consequences

- One run per clone or worktree. Aspire stops a clone's running AppHost before starting it again, even with `--isolated` ("To run multiple isolated instances simultaneously, run from different directories such as git worktree directories"), so a second run of the same code is a second git worktree. `dev.ps1` was to have allowed several runs from one clone, but that would have needed the custom build folders this decision rules out.
- The first run on the machine can be plain `aspire start`, on the ports the projects declare (the server's launch profile, the dashboard's in the AppHost's); every further run is `aspire start --isolated`. Vite's port is chosen by Aspire even in a plain run, and an isolated run's URLs are all random, so they're read from `aspire describe --format json` rather than known in advance.
- `aspire start` returns once the AppHost is up, not the app; `aspire wait web` waits until the browser app answers (after the server's `/health` check passes, which it waits for).
- Every run starts on the scenario and speed in `appsettings.Development.json` (ADR-0009); another is picked afterwards, in the app or through the run's own server URL. The scenario at start is no longer a command-line option.
- The Aspire CLI is a new prerequisite for running locally (not for building or testing), and the run is HTTPS by default, so the ASP.NET Core development certificate must be trusted once (`aspire certs trust`); without that the server's health check fails and the browser app waits for it.
- A run uses the clone's normal build (`bin\Debug`), which `dotnet test` and `dotnet build` build into too. While a run is going, they build and pass as long as the server is unchanged since the run started; after a change to it, the build fails, unable to replace the running `ScoreMap.Server.exe`. So stop the run before building a changed server. `dev.ps1` built into a folder of its own to avoid this; Aspire has no such option, and a custom build folder is ruled out.
- The ServiceDefaults are the template's, but for one line: OpenTelemetry for the dashboard (exported only where Aspire sets an endpoint, so not when deployed), `/health` and `/alive` in Development only, and service discovery on every HttpClient. The template's standard resilience handler (Polly's retries and timeouts on every HttpClient) is left out, as Aspire expects service defaults to be fitted to the app: ScoreMap's clients each set their own timeout and the poller retries on its next poll, its retries would get round the Nominatim rate limit, and its timeouts run on the app's `TimeProvider`, which the server tests replace with a clock they move by hand, so a test with a site that never answers hung.
- Deployment is unchanged (ADR-0007): `dotnet publish` of the server alone, not through Aspire.
