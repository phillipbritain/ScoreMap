# Configuration

How the server finds games and venues, and the files and settings that shape them. Files named here are under `server/src/ScoreMap.Server/`, and commands run from the repo root.

## Leagues

The leagues shown are listed under `Leagues` in `appsettings.json`. Each has a `Key` (ESPN's `{sport}/{league}`, optionally with scoreboard options after a `?`), a display `Name`, its `Sport` (`"Football"`, `"Basketball"`, `"Baseball"`, `"Hockey"`, `"Soccer"`, `"Cricket"`, `"Rugby"`, `"Tennis"`, `"Racing"`, `"Golf"` or `"MMA"`; anything else stops the server at startup; a cricket league's key is ESPN's numeric id for the competition, such as `cricket/8048` for the IPL, and so is a rugby league's, such as `rugby/180659` for the Six Nations), and optionally `RegulationPeriods` when it plays a different number of periods from its sport's usual (2 halves in men's college basketball, 7 innings in college softball), and `PeriodMinutes` when its periods run a different length on the game clock (20-minute halves in men's college basketball, 10-minute quarters in women's basketball; only scenarios use it). `PlannedLength` (a time span such as `"03:15:00"`, default 3 hours) is how long the league's games usually take from start to finish. ESPN gives no end times, so the server uses it to estimate when a game ended when it first sees the game already Final (for instance after sleeping), since a Final game keeps its pin 5 minutes after it ends (ADR-0005, ADR-0021). A college league may list its `Conferences`, each with ESPN's group `Id` for it and the short `Name` a viewer picks it by (`{ "Id": "8", "Name": "SEC" }`), so the viewer can narrow the league to some of them in Leagues on the rail. ESPN's ids differ from sport to sport (the SEC is 8 in football and 23 in basketball), and its scoreboard gives a team's conference only in football and basketball; a team in none of a league's listed conferences belongs to none.

## Polling

The server reads each league's games from ESPN's scoreboards for yesterday and today (and, within 3 hours of midnight, tomorrow), in US Eastern days as ESPN keeps them. Optional last-score details arrive on a later poll without delaying basic scores; see [ESPN requests and caching](espn-data.md#requests-the-server-makes).

While at least one browser is connected, the server polls each league about every 15 seconds while it has Live games and every 3 minutes otherwise, and pushes change events to browsers over SignalR. With no browser connected it doesn't poll at all. A connecting or reconnecting browser waits up to 5 seconds for any league scoreboards its connection had to fetch afresh (the board cold, or idle long enough for them to fall due), so that its first games aren't empty or out of date, then up to 250 ms more for other fresh data, then gets the current board. A league fetch already under way for the browsers watching holds no one past the 250 ms. Pending requests deliver changes afterward. At most four feed requests run at once; independent leagues do not wait for a slow league or Top Events. Venue lookups run separately. Corrections, given positions, checked-in scenario and league lookups, and saved lookups (including misses along the fallback chain) are answered immediately, so known venues are placed in the join snapshot even while another search is pending in the same league or another league. Pending games keep their last known position for the same venue; otherwise they go out unplaced (no position or time zone) until the lookup finds them, and the globe leaves them off the map while they stay in the Events list. Nominatim keeps its application-wide rate limit. Scenario switches cancel obsolete work and discard late results.

## Highlights

The Videos tab lists clips from the event’s ESPN summary, newest first. Eligible clips open in the in-app player, and each row links to the original ESPN page. Set `Highlights__EspnDirect=false` to use ESPN page links only. While a Final event’s Videos tab stays open, it continues checking for new ESPN clips.

## Venues

The server looks each venue up once through OpenStreetMap Nominatim, saving the results to `data/venue-locations.json` (git-ignored; delete it to look venues up again). It also finds each venue’s photo for the event panel using ESPN. It checks the event’s league first, then another league that plays at the same venue (MLS’s Soldier Field uses the NFL’s photo). Within each league it prefers the interior photo, then the day photo, and skips images ESPN reports as narrower than 720 pixels. Without a suitable photo, the panel shows its plain header. Results are saved to `data/venue-photos.json` (git-ignored). The switch to ESPN-only invalidates the prior cache once, so earlier Wikimedia photos disappear and venues are looked up again as needed. NASCAR's and golf's scoreboards give no venue, so the server asks ESPN's core API for each race's or tournament's venue once, saving it to `data/event-venues.json` (git-ignored too; delete it to ask again). It asks the same for each NASCAR race's car numbers once the race lists its field, keeping them only while it runs (ADR-0031). Each clone or worktree has its own `data/`.

So that a cold start (a first deploy, or a wiped `data/`) doesn't have to wait on Nominatim, the live leagues' venues are looked up in advance and checked in as `league-venue-locations.json`: each query the server would ask for a game's pin (the venue, its city, the home team's city), mapped to its position, or to null where Nominatim found nothing. The server answers from it after the scenario lookups and before its saved lookups, and never writes it. To refresh it, say at the start of a season or after adding a league, run `dotnet run scripts/lookup-league-venues.cs` (30 days back to 30 ahead, or pass a first and last date after `--`), which reads every configured league's scoreboards from ESPN and asks Nominatim, at its pace, only the queries the file doesn't have yet; then check it in.

The saved location and photo files are disposable caches. If either cannot be read, the server logs a warning and starts with an empty cache; malformed JSON is moved aside with a `.corrupt-<unique id>` suffix when possible. Lookups still follow Nominatim's request limit. If saving fails, the server logs a warning and keeps the answers in memory until restart; a later new answer tries saving again. This recovery applies only to runtime caches, not checked-in scenario venue data or configuration.

ESPN gives no venue for an IndyCar race anywhere, so each race's track comes from `indycar-tracks.json` (checked in), which maps the race's name as ESPN gives it to its track, for example `"Grand Prix of Long Beach": { "name": "Streets of Long Beach", "city": "Long Beach", "region": "CA", "country": "USA", "latitude": 33.7633, "longitude": -118.1924 }`. Its position is the pin's, without a lookup. A race missing from it isn't shown, and the server logs a warning naming it ("No track for the race …"); add it, and it shows from the next poll, without a restart. The file covers the 2026 calendar; check a new season's race names against ESPN's (see [espn-data.md](espn-data.md)).

Venue lookups can be wrong (e.g. a stadium placed in a same-named town). To fix a pin, add the venue's name and the right position to `venue-corrections.json`, for example `"Lincoln Financial Field": { "latitude": 39.9008, "longitude": -75.1675 }`. Corrections override any lookup, and a track list's position, and take effect from the next poll, without a restart. When a venue can't be found, its pin goes to the center of its city; when a game has no venue, to the home team's city.

## Scenario venues and teams

Scenarios (ADR-0009) put their games at the real venues listed in `scenario-venues.json` (ADR-0028), each with the configured leagues that play there (each with ESPN's id for the venue, its city, region and country as that league's scoreboard gives them, and its home teams there; none at a neutral site) and the groups it belongs to (`worldwide`, `big-cities`, `london`, `london-and-nearby`, `new-york`, `los-angeles`, `us-college`, `written-out`). A game there is in one of its leagues, at home to that league's team there. A filled game's teams come from `scenario-teams.json` beside it, which lists each configured league's real teams (so NFL teams only play NFL teams), and no team is in two games at once; run `dotnet run scripts/update-scenario-teams.cs` to rebuild it from ESPN after adding a league to the configuration or when a league's teams change, and check it in.

A game written out in a scenario file must be at a venue in this list (by name; a city written must be its league's there) where its league plays, at home to its team there, or else be marked `"notInVenueList": true` as made up on purpose; anything else stops startup. Their positions are checked in as `scenario-venue-locations.json` beside it, which the server uses before its saved lookups, so scenario venues never wait on Nominatim. After changing the venue list, run `dotnet run scripts/lookup-scenario-venues.cs` to look up the new venues (it lists any it can't find), and check both files in.

The venue list, team list and venue lookups ship to production with the `worldwide` scenario file (and no other), since a demo shows it on the live site (ADR-0019).

## Stream links

The event panel shows unofficial stream links (hobby v1 only, ADR-0002). `StreamFinder:Sites` in `appsettings.json` configures the sites; the shipped site reads StreamEast's schedule at `https://streameast.cool/` and extracts direct game links. Remove the configured sites to switch the finder off. The event panel shows only StreamEast's links, each as StreamEast's logo, the first two shown and the rest counted in “+N more.” Stream-finder settings are read at startup; restart the server after editing them.

The finder starts a background fetch when an Upcoming or Live game with two sides needs an uncached schedule. All games and viewers using the same site and resolved page URL share that fetch and its parsed listings. A fetch has a short timeout (`TimeoutSeconds`, default 3); successful, empty and failed results are cached for `CacheMinutes` (default 10, shipped setting 2). Expired listings are omitted while refreshing, and failed refreshes remove old links. No fetch blocks scores. New links reach the browser on the next league poll after discovery, normally within 15 seconds for live leagues or 3 minutes for quiet leagues. Fetches happen only when games need them, rather than on a separate timer.

Each site has a `Name`, `SearchUrl` and `LinkPattern`. A fixed schedule URL shares one fetch across games; search URLs can still use `{query}` (both teams), `{away}` or `{home}`, URL-escaped. The regular expression extracts `href`, `first` and `second` side names, optionally `league` and `start`. Simple sites can instead extract `text` containing exactly “Team A vs Team B.” Links must be HTTP(S), have no credentials and stay on the configured page's authority.

Matching compares complete side names, ignoring case, accents, punctuation and extra spaces, in either order. `LeagueAliases` maps ScoreMap league names to site categories; when configured, missing or unmapped categories are rejected. `TeamAliases` lists explicit alternate names under a ScoreMap league and full team name, for example `"NCAA Men's Basketball": { "UCLA Bruins": ["UCLA"] }`. Aliases apply only within that league; nickname-only or partial-name guesses are not used. Each site contributes a link only if exactly one distinct URL matches. Repeated anchors for the same URL count once; multiple matching games are omitted.

When a listing supplies `start`, it must be an ISO 8601 timestamp with an explicit time zone and within 30 minutes of the game's scheduled start. Malformed timestamps are rejected. StreamEast currently exposes only relative display times, so its shipped pattern leaves `start` absent: matching relies on the current schedule, league and complete side names, and cannot verify the date or distinguish an unlisted rematch. Unknown abbreviated names and unsupported categories yield no link until explicitly mapped. Fields and fight cards have no two-side match and get no links from this finder.

The finder sits behind `IStreamLinkSource`; before any public launch remove it by deleting `WatchLinks/StreamFinder*.cs` and the `AddStreamFinder` line in `Program.cs`, after which a no-op source gives every game no stream links (optionally also drop `Game.StreamLinks`, `web/src/panel/streamLinks.ts` and its line in `EventPanel.tsx`).

## Feedback

The Feedback button's notes are filed as issues in this repo, labeled `needs-triage` and `feedback`, by the server with the owner's token. ScoreMap has no sign-in, so a browser never posts. The token is the setting `Feedback:GitHubToken` (in production, `Feedback__GitHubToken`). Use a fine-grained token scoped to this repo with Issues read and write access. In production, Container Apps reads it from [Key Vault](deploy.md#feedback-vault). In production the server warns at startup when it has no token. With no token, as on local runs and in tests, the server logs the issue it would have filed and thanks the viewer with a link to the repo's issues. `Feedback:Repository` (default `phillipbritain/ScoreMap`) is the repo, and `Feedback:TimeoutSeconds` (default 10) how long GitHub gets to answer.

Feedback takes 10 to 2,000 characters, and each visitor (by IP address, which is checked but never stored or posted) can send 3 in 10 minutes; after 20 issues in a day (UTC), the rest get "Feedback is closed for today, try tomorrow". A submission with the hidden honeypot field filled in is thanked but dropped. The issue's Context section gives the app's version (commit), the screen size and layout, the browser and OS, the open game and the leagues showing, but never the viewer's address, location or time zone. In production the visitor's address comes from the ingress's `X-Forwarded-For` header, which the app reads through the [forwarded headers setting](deploy.md#app-settings).
